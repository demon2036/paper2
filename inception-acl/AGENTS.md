# AGENTS.md

本文件是本项目的常驻约定。每个新会话开始时要遵守。

### 并发安全

多个 agent 同时写同一个文件会互相覆盖。

**同一个主题文件同一时间只由一个会话写。** 需要并行写多个主题时，各写各的文件。

---

## 四、语言要求（硬性）

**`memory/` 下的所有内容必须用中文写。**

这条要强调。英文只允许出现在两种位置。

1. **原文引用** —— prompt 逐字、判审返回的理由原文、报错原文、文献标题。
2. **代码与路径** —— 文件名、变量名、命令、URL。

除这两类，一律中文。**包括小标题、表格表头、注释、说明文字。**

---

## 五、表达规范

以下原则借鉴 ASD-STE100，用于中文技术写作。

**先说明这个概念是什么，再解释它怎样工作。**
读者需要先有定义，才能理解机制。

**使用短句。每段集中解释一个问题。**
一段里塞两个话题，读者会分不清因果。

**保持句子之间的因果和转折关系。**
不要只罗列事实，要写清楚为什么 A 导致 B。

**同一个概念始终使用同一个名称。专业术语首次出现时，解释它的含义。**
在同一个文档里换用同义词描述同一个东西，读者会以为你在说两件事。

**写清楚谁执行动作，以及动作作用于什么对象。**
「超时 75 秒」要写成「实验脚本在 75 秒后放弃等待，记为 HANG」。

**解释操作时，按实际顺序分步写。**
先发什么、再读什么、最后判断什么。

**保留必要的条件、例外和不确定性。不要为了简短而省略关键内容。**
实验结论尤其如此：通过率必须带分母和批次号。

**用具体例子帮助理解。**
抽象描述容易产生歧义，一个真实的 prompt 片段能消除它。

**将事实、推断和建议分开表述。**
「实测 22/47 通过」是事实；「所以姿势不影响等级」是推断；「下次优先试 X」是建议。
三者混在一句里，读者无法判断哪部分是可靠的。

## 六、项目硬约束



其中最容易违反的两条，这里重复一遍。

1. **只用 `/v1/images/generations`（纯 gen）。** 用户原话：
   「我们这里不做 edit 的，不能通过 edit 好图就说 ok」。edit 结果只能当机制分析。
2. **所有长任务挂后台，不要 `sleep` 阻塞。**
   `setsid nohup python3 x.py > x.log 2>&1 < /dev/null & disown`
